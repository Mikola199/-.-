# EQUHUB — Единая цифровая платформа

## Документ 9: План информационной безопасности

### 1. Стратегия безопасности EQUHUB

Обеспечение безопасности пользовательских данных, баланса кошельков и конфиденциальности переписки в мессенджере является критическим приоритетом платформы EQUHUB. Защита реализуется на всех уровнях: сетевом, транспортном, прикладном и уровне баз данных.

---

### 2. Аутентификация и авторизация (JWT & 2FA)

#### 2.1. JWT-токены
*   **Спецификация:** Токены авторизации генерируются по промышленному стандарту **JWT HS256 (HMAC-SHA256)** с использованием встроенного криптографического модуля (`crypto`) в Node.js / Next.js и библиотеки `python-jose` на Auth-сервисе.
*   **Срок действия и Claims:**
    *   `Access Token`: 15 минут. Содержит зашифрованный payload с обязательным утверждением времени истечения (`exp` claim) и идентификатора пользователя (`userId`, `email`). Используется для авторизации запросов в заголовке `Authorization: Bearer <token>`.
    *   `Refresh Token`: 30 дней. Хранится строго в защищенной куке (`HttpOnly`, `Secure`, `SameSite=Strict`) для предотвращения XSS атак.
*   **Верификация и Ротация ключей:** Подпись токена валидируется микросервисами локально с помощью общего секрета. Ключи подписи ротируются каждые 90 дней через HashiCorp Vault. Любые запросы с просроченным `exp` или некорректной подписью незамедлительно отклоняются кодом 401.

#### 2.2. Двухфакторная аутентификация (2FA)
*   Используется алгоритм **TOTP (RFC 6238)**.
*   При включении 2FA генерируется секретный ключ, который пользователь импортирует в приложение Google Authenticator или Яндекс Ключ с помощью QR-кода.
*   Проверка OTP-кода обязательна при входе с нового устройства, выводе средств из кошелька или переводе безопасной сделки на шаг завершения.

### 3. Безопасность прикладного уровня (API Endpoints & Messages)

#### 3.1. Защита маршрута обмена сообщениями (`POST /api/messages`)
Для предотвращения атак обхода авторизации (Bypass Authorization, CWE-862) и подделки личности отправителя (Spoofing) эндпоинт отправки сообщений полностью защищен:
1.  **Проверка JWT-токена:** Маршрут в обязательном порядке извлекает заголовок `Authorization: Bearer <token>` и валидирует его через `verifyJwt(token)`. Запросы без токена или с невалидным/просроченным токеном возвращают ошибку `401 Unauthorized`.
2.  **Идентификация отправителя:** Поле `from` (отправитель сообщения) принудительно вычисляется на сервере на основе декодированных данных из верифицированного JWT-токена (`payload.userId`), а не берется из JSON-тела запроса.
3.  **Защита от спуфинга (Spoofing Prevention):** Если клиент пытается явно указать поле `from` в теле запроса, отличное от его реального `userId` (или `email`) из токена, сервер пресекает операцию и возвращает ответ `403 Forbidden` ("Cannot send message as another user").

### 4. Криптография и хранение учетных записей

*   **Хэширование паролей:** Категорически запрещено хранить пароли в открытом виде. Для хэширования используется современный и криптостойкий алгоритм **Bcrypt (Passlib)** с динамической солью и фактором сложности (Work Factor) равным `12`.
*   **Шифрование данных в БД:** Конфиденциальные данные профиля (контакты, приватные ключи кошелька) шифруются на лету алгоритмом **AES-256-GCM** на уровне приложения перед записью в СУБД PostgreSQL.

---

### 5. Резервное копирование и восстановление (RPO, RTO и Метрики)

Для соответствия строгим параметрам непрерывности бизнеса установлены измеримые критерии успешности резервного копирования:

*   **Резервное копирование (PostgreSQL):** Автоматический бэкап (pg_dump) выполняется каждые 24 часа. Срок хранения (retention policy) составляет 30 дней.
*   **Мониторинг и Оповещение:** Статус завершения бэкапа проверяется автоматическим демоном; в случае сбоя или задержки отправляется критическое оповещение дежурному администратору в Telegram и PagerDuty.
*   **Целевая точка восстановления (RPO):** Максимум 24 часа. Достигается ежедневным копированием и трансляцией логов транзакций (WAL-G).
*   **Время восстановления (RTO):** Менее 2 часов.
*   **Учения и восстановление:** Проводятся обязательные ежемесячные тестовые восстановления баз данных в изолированную песочницу со сверкой целостности данных. Ключи шифрования бэкапов дублируются на резервных серверах по протоколу разделения секрета Шамира.

#### Исполняемый план (Runbook) восстановления БД:
```bash
# 1. Остановить трафик на API Gateway
kubectl scale deployment api-gateway --replicas=0

# 2. Инициализировать чистый инстанс базы данных
pg_restore -U equhub_admin -d equhub_db -h postgres-replica /backups/latest.dump

# 3. Накатить WAL логи для минимизации потерь до RPO
wal-g restore-seek latest

# 4. Проверить целостность и запустить шлюз
kubectl scale deployment api-gateway --replicas=2
```
