# EQUHUB — Единая цифровая платформа

## Документ 9: План информационной безопасности

### 1. Стратегия безопасности EQUHUB

Обеспечение безопасности пользовательских данных, баланса кошельков и конфиденциальности переписки в мессенджере является критическим приоритетом платформы EQUHUB. Защита реализуется на всех уровнях: сетевом, транспортном, прикладном и уровне баз данных.

---

### 2. Аутентификация и авторизация (JWT & 2FA)

#### 2.1. JWT-токены
*   **Спецификация:** Токены авторизации генерируются по стандарту **JWT HS256 (HMAC-SHA256)** с использованием библиотеки `python-jose` на Auth-сервисе.
*   **Срок действия:**
    *   `Access Token`: 15 минут. Используется для авторизации запросов в заголовке `Authorization: Bearer <token>`.
    *   `Refresh Token`: 30 дней. Хранится строго в защищенной куке (`HttpOnly`, `Secure`, `SameSite=Strict`) для предотвращения XSS атак.
*   **Подпись:** Подпись токена валидируется микросервисами локально с помощью общего секрета, полученного из HashiCorp Vault.

#### 2.2. Двухфакторная аутентификация (2FA)
*   Используется алгоритм **TOTP (RFC 6238)**.
*   При включении 2FA генерируется секретный ключ, который пользователь импортирует в приложение Google Authenticator или Яндекс Ключ с помощью QR-кода.
*   Проверка OTP-кода обязательна при входе с нового устройства, выводе средств из кошелька или переводе безопасной сделки на шаг завершения.

---

### 3. Криптография и хранение учетных записей

*   **Хэширование паролей:** Категорически запрещено хранить пароли в открытом виде. Для хэширования используется современный и криптостойкий алгоритм **Bcrypt (Passlib)** с динамической солью и фактором стоимости (Work Factor) равным `12`.
*   **Шифрование данных в БД:** Конфиденциальные данные профиля (контакты, приватные ключи кошелька) шифруются на лету алгоритмом **AES-256-GCM** на уровне приложения перед записью в СУБД PostgreSQL.

---

### 4. Сетевая безопасность и защита от атак

*   **Rate Limiting (Ограничение частоты запросов):** На уровне API Gateway (Nginx) настроены лимиты запросов во избежание Brute Force и DDoS-атак:
    *   Маршруты авторизации: максимум 5 запросов в минуту с одного IP.
    *   Обычные GET запросы: максимум 100 запросов в секунду с одного IP.
*   **HTTPS & TLS:** Разрешены только защищенные соединения по протоколу **HTTPS/TLS 1.3**. Шифры устаревших версий TLS 1.0 и 1.1 полностью отключены.
*   **CORS (Cross-Origin Resource Sharing):** Политика CORS строго ограничивает перечень доверенных доменов. Запрещено использовать `Access-Control-Allow-Origin: *`.
*   **Защита WebRTC:** Сигнальный трафик шифруется по TLS, а сам медиапоток передается напрямую между пирами в зашифрованном виде по протоколу **SRTP (Secure Real-time Transport Protocol)** с обменом ключами DTLS.

---

### 5. Резервное копирование и восстановление

*   **Частота резервных копий (PostgreSQL):** Каждые 24 часа в автоматическом режиме создается полный бэкап (pg_dump), шифруется и загружается в изолированное хранилище холодного резерва.
*   **Точка восстановления (RPO):** Максимум 1 день.
*   **Время восстановления (RTO):** Менее 2 часов для возобновления полной дееспособности платформы в случае катастрофических сбоев.
