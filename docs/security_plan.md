# План обеспечения информационной безопасности EQUHUB

Настоящий документ содержит детальное описание мер, протоколов и архитектурных решений по информационной безопасности Единой цифровой платформы **EQUHUB** в соответствии с Разделами 9 и 15 (Пункт 9) Требований к программному обеспечению (SRS).

---

## 1. Аутентификация и сессионный контроль (Authentication)

Надежная идентификация пользователей и защита сессий реализованы через двухфакторную аутентификацию (2FA) и механизм защищенных токенов доступа.

### 1.1 Механизм JWT (JSON Web Tokens)
* **Алгоритм подписи:** **HS256** (HMAC-SHA256). Секретные ключи для подписи JWT хранятся как Kubernetes-секреты (Secrets) и никогда не жестко вшиваются в код.
* **Разделение токенов (Access & Refresh):**
  * `access_token` выпускается со сроком действия **15 минут**, хранится на клиенте в оперативной памяти (In-Memory) или изолированном стейте приложения для исключения XSS кражи.
  * `refresh_token` выпускается со сроком действия **30 дней**, хранится в безопасном хранилище мобильного устройства (Flutter Secure Storage) или в куках веб-браузера с флагами `HttpOnly`, `Secure` и `SameSite=Strict` для предотвращения CSRF-атак.
* **Управление библиотеками:** В `Auth Service` валидация и генерация JWT производится с помощью библиотеки `python-jose`.

### 1.2 Хэширование паролей
* Пароли пользователей никогда не хранятся в открытом виде. Хэширование выполняется в `Auth Service` с использованием надежной библиотеки `passlib` и криптографического алгоритма **bcrypt** с солью (Salt) и фактором сложности не менее 12.

### 1.3 Двухфакторная аутентификация (2FA)
* Реализован TOTP (Time-Based One-Time Password) алгоритм (RFC 6238). При активации 2FA пользователь сканирует QR-код (сгенерированный секрет TOTP), и при каждом входе система запрашивает одноразовый 6-значный цифровой код из приложения Google Authenticator / Яндекс Ключ.

## 2. Безопасность передачи данных (Cryptography & Transport)

* **Шифрование трафика (Transit):** Все сетевое взаимодействие между клиентом и сервером защищено протоколом **HTTPS** (порт 443) и **WSS** для вебсокетов с обязательным использованием **TLS 1.3** (или TLS 1.2 в качестве совместимого минимума).
* **SSL сертификаты:** Автоматическое получение и продление доверенных сертификатов обеспечивается через службу **Let's Encrypt** в связке с автоматизированным контроллером Ingress кластера Kubernetes.
* **Шифрование хранимых данных (At Rest):** Конфиденциальная информация в СУБД PostgreSQL шифруется на уровне колонок (pgcrypto) или на уровне дисковых томов инфраструктуры (LUKS). Все резервные копии баз данных архивируются и шифруются с использованием симметричного шифрования AES-256.

## 3. Защита API от угроз и атак (Threat Mitigation)

Для предотвращения сетевых атак и перегрузки серверов (DDoS, Brute Force) на уровне API Gateway (Nginx/Kong) и приложении реализованы следующие защитные механизмы:

### 3.1 Ограничение частоты запросов (Rate Limiting)
* Для неавторизованных роутов (логин, регистрация): лимит до **5 запросов в минуту** с одного IP для предотвращения брутфорса паролей.
* Для стандартных авторизованных API роутов: лимит до **100 запросов в секунду (RPS)** на один IP-адрес. Превышение лимита возвращает статус `429 Too Many Requests`.

### 3.2 Предотвращение инъекций (Injection Protection)
* Использование ORM (Prisma/TypeORM в NestJS и SQLAlchemy/SQLModel в FastAPI) гарантирует автоматическое параметризованное выполнение SQL-запросов, полностью исключая атаки класса **SQL Injection**.
* Все текстовые данные, вводимые пользователями на маркетплейсе или в социальной сети, проходят строгую санитизацию на бэкенде для вырезания вредоносных HTML/JS-тегов (защита от **XSS**).

### 3.3 CORS (Cross-Origin Resource Sharing) политики
* Настройки CORS строго ограничивают доступ к API. Разрешены запросы только от подтвержденных доменных имен EQUHUB (например, `https://equhub.ru` и `https://admin.equhub.ru`). Использование подстановочного символа `Access-Control-Allow-Origin: *` в промышленном окружении категорически запрещено.

## 4. Конфиденциальность данных и аудит (GDPR / ФЗ-152)

* **Соответствие требованиям 152-ФЗ:** Все персональные данные пользователей Единой цифровой платформы EQUHUB на территории РФ хранятся и обрабатываются на серверах, физически расположенных в российских дата-центрах.
* **Логирование безопасности (Audit Trail):** В соответствии с Разделом 4 SRS, любые критические действия пользователей (смена пароля, перевод средств в кошельке, вход с нового устройства, изменение настроек приватности) фиксируются в специальной таблице `audit_logs` с записью IP-адреса, даты, типа действия и отпечатка браузера/устройства (User Agent). Доступ к этой таблице открыт только роли `Super Admin`.
